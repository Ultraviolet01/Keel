## What protects the money

Each claim names the code that enforces it. Line numbers are for the vault code the factory deploys now (`DzEvdU91cjWgXyue5tDh9BkWwv4kVvmYdtmBmJAHPHr6`).

- **Vault code cannot change under the owner.** The vault has no upgrade or migrate method, and the factory never redeploys a vault: it deploys the code once when it creates the vault (the factory's own private `migrate` only converts the factory's state when the factory itself is upgraded, and cannot touch a vault) ([`lib.rs:180`](../factory/src/lib.rs#L180)), and `set_vault_code` only changes the code for vaults created later. Not Keel, not the factory admin, can swap a vault's rules for looser ones. The other side: fixes reach new vaults only.
- **Keel's key reaches three methods.** The factory adds Keel's key in the same transaction that creates the vault, as a NEAR function-call key limited to `execute_payment`, `propose_payment` and `recall_from_yield` with a 0.25 NEAR gas allowance ([`lib.rs:181`](../factory/src/lib.rs#L181), [`lib.rs:103`](../contract/src/lib.rs#L103)). It cannot transfer NEAR, add keys, change the rules, approve or touch another vault. The vault also checks that Keel's key signed each call ([`internal.rs:84`](../contract/src/internal.rs#L84)), and owner methods need 1 yoctoNEAR, which a function-call key cannot attach ([`internal.rs:94`](../contract/src/internal.rs#L94)).
- **One agent key for every vault.** The factory adds the same Keel key to every vault it creates, and the hosted agent keeps it in one GitHub Actions secret. Whoever holds it can act as Keel on every vault at once, but only inside each vault's own rules above: owner bills, approved payees, caps and buffer. Each owner can replace it on their vault with their own key (`set_agent_key`) and run the agent themselves, or remove it (`revoke_agent`).
- **No other keys on the vault.** Nobody, Keel included, can sign as the vault outside its rules.
- **Every agent payment pays a bill the owner set.** `execute_payment` and `propose_payment` refuse a call without a `bill_ref` ([`lib.rs:421`](../contract/src/lib.rs#L421), [`lib.rs:592`](../contract/src/lib.rs#L592)). `check_agent_ref` ([`internal.rs:138`](../contract/src/internal.rs#L138)) then requires that it names a bill the owner listed, paid to that bill's payee for its exact amount; a top-up (`top:`) only to a card or own wallet with a target balance, up to that target, dated today; idle cash (`idle:`) only to a yield destination, up to its per-move limit, dated today. A monthly or yearly bill can only be paid for its own periods, from its first due date to next month or next year ([`rules.rs:43`](../contract/src/rules.rs#L43)). So a stolen agent key can pay only the owner's own bills, to their payees, for their amounts, once each, inside the caps.
- **A waiting proposal cannot be swapped.** A newer proposal for the same bill replaces the waiting one ([`lib.rs:618`](../contract/src/lib.rs#L618)), but it passes the same `check_agent_ref` first ([`lib.rs:594`](../contract/src/lib.rs#L594)), so it cannot change the payee or the amount of a NEAR or EVM bill. A NEAR Intents proposal for a cross-chain bill cannot name the bill's payee, because it pays the quote's deposit address, which changes with every quote. The vault still bounds it ([`internal.rs:213`](../contract/src/internal.rs#L213)): the receiver must be a 64-character implicit account, the shape of a 1Click deposit address on NEAR, and the amount at most 3% over the bill (Keel's agent refuses quotes above that too). So a stolen key cannot redirect a cross-chain bill to an ordinary account or inflate it, even for an owner who approves from a multisig interface or the command line. Within those bounds the owner must still check where the address pays: the app asks 1Click before approval (`checkDeposit`, [`intents.ts:68`](../web/src/intents.ts#L68)), and every Intents payment needs the owner's approval.
- **Each bill is paid once.** The vault records every bill it pays and refuses a second payment ([`internal.rs:289`](../contract/src/internal.rs#L289)), even after Keel restarts with no memory. A failed transfer frees the bill again ([`internal.rs:40`](../contract/src/internal.rs#L40)). A top-up or idle-cash move must be dated today (UTC), so each wallet gets at most one per calendar day. A top-up is paid only if the card or own wallet would end at or under its target: the vault reads the wallet's balance from the token contract first and refuses otherwise ([`lib.rs:503`](../contract/src/lib.rs#L503)), so a stolen key cannot fill a full wallet.
- **The daily cap is a rolling 24 hours.** The vault keeps each agent payment's time and amount and counts the last 24 hours ([`internal.rs:103`](../contract/src/internal.rs#L103), checked in [`internal.rs:243`](../contract/src/internal.rs#L243)), so the cap cannot be spent twice across midnight. A failed payment is given back ([`internal.rs:122`](../contract/src/internal.rs#L122)), and so is an EVM bill whose MPC signature failed ([`lib.rs:1389`](../contract/src/lib.rs#L1389)).
- **Routine cross-chain bills, inside limits only.** An EVM bill is signed without the owner only up to that chain's `auto_cap` ([`lib.rs:448`](../contract/src/lib.rs#L448)), to an allowlisted 0x payee, inside the per-payment and daily caps, and the cap itself cannot be above the per-payment cap ([`lib.rs:738`](../contract/src/lib.rs#L738)). Without an auto cap, every payment on another chain waits for the owner.
- **Cash buffer on chain.** With a buffer set, the vault reads its own balance from the token contract before each payment by Keel, counts every other payment still in flight, and refuses if the buffer would break, undoing the spend and the bill mark ([`lib.rs:1203`](../contract/src/lib.rs#L1203)).
- **Only the owner lists bills and payees.** `add_bill` and `add_payee` are owner methods ([`lib.rs:943`](../contract/src/lib.rs#L943), [`lib.rs:1083`](../contract/src/lib.rs#L1083)). A phished invoice or a compromised agent cannot add work or destinations for Keel; a listed bill still goes through the same bands.
- **The yield investment only comes back to the vault.** `recall_from_yield` withdraws only from a lending market the owner approved ([`lib.rs:1146`](../contract/src/lib.rs#L1146)), and Rhea lending (formerly Burrow) pays withdrawals only to the depositing account, the vault.
- **The AI can only make Keel stricter.** Before Keel pays alone, an LLM (NEAR AI Cloud, or Claude) reviews the bill, what the payee was paid before and the owner's other payees, and answers `ok`, `propose` or `refuse`. `stricter` ([`review.ts:72`](../agent/src/review.ts#L72)) applies only a move toward caution: a payment becomes a proposal or a refusal, never the reverse. Its reason goes on the proposal and in the log. The check runs for bills paid on NEAR and for cross-chain bills paid alone under an auto cap, with the same view of the payee's history and the owner's other payees. It fails open: if the model times out, is unreachable or answers in the wrong shape, Keel follows its rules as if the check said `ok`. That is deliberate, since the check is an extra layer and the vault is the hard limit: even with no model, or a fooled one, nothing outside the bills, payees and caps above can be paid.
- **Invoice text is untrusted.** It never reaches the model that writes proposal reasons ([`explain.ts:41`](../agent/src/explain.ts#L41)); the review model gets it last, quoted and labelled as written by the payee ([`review.ts:39`](../agent/src/review.ts#L39)). The app shows it quoted and marked unverified. Invoice reading returns a draft whose values are re-checked, and an address from an invoice that is not an approved payee is flagged and always needs approval.
- **A stolen agent key cannot flood the vault.** At most 50 proposals wait at once ([`lib.rs:641`](../contract/src/lib.rs#L641)), every proposal needs one of the owner's bills, and Keel's calls are refused once the vault's spare NEAR would fall under 0.2 ([`internal.rs:280`](../contract/src/internal.rs#L280)). The owner can always approve, pause, withdraw and remove Keel's key.
- **The founder can fire Keel.** `revoke_agent` deletes the key in one transaction ([`lib.rs:884`](../contract/src/lib.rs#L884)); `set_agent_key` adds one back.
- **Optional multisig owner.** A vault can be handed to a Sputnik DAO multisig; then no single wallet can change the rules, approve a payment or withdraw, and Keel's key stays limited to the same three methods. The hand-over takes two steps, an offer by the owner ([`lib.rs:1000`](../contract/src/lib.rs#L1000)) and an acceptance by the multisig's vote ([`lib.rs:1044`](../contract/src/lib.rs#L1044)), so nobody can push a vault already set up with their own payees and bills onto a team. The factory and the vault both record the new owner, and the app warns if they disagree. Before members vote, the app shows each proposal's exact calls and arguments, not only its description. Sputnik DAO lets anyone file a proposal by default (only members vote), which lets outsiders fill a team's vote list for a bond. Multisigs created from Keel let only members file. On an older, open multisig the **Multisig owner** card says so and offers **Only members can propose**, a policy change members vote on; until then the app marks every proposal filed by a non-member, and Keel emails vote requests only for proposals filed by members (the daily digest counts the others). Editing and voting controls go only to members whose role allows them.
- **Notifications cannot be forged or hijacked.** Signing up needs a message signed by one of the account's full-access keys ([`_notify.ts:110`](../web/api/_notify.ts#L110)), and the email must be confirmed by its link. The agent's round report is signed with Keel's agent key and checked against the factory's record ([`_notify.ts:132`](../web/api/_notify.ts#L132)); the server re-reads every vault from the chain instead of trusting the report. Addresses are kept in a private store and deleted by the unsubscribe link. Whether an account gets alerts, and at which (masked) address, is told only to that account: the app remembers it in the browser after confirming, and **Check my status** asks the server with a wallet-signed message. The public status lookup says only whether email is set up on the deployment.
- **Invoice reading is for Keel's own pages.** The endpoint refuses requests without an `Origin` header or from another site, and limits each visitor to 10 invoices an hour. A script can still forge the header, so this slows abuse of the deployment's Claude key rather than preventing it.
- **Rule changes are public.** Every `update_policy` emits the old value, new value, reason and approver ([`lib.rs:816`](../contract/src/lib.rs#L816)).

**Counterparty check:** before any payment, Keel scores the payee.
